The CSBoard API enforces per-key rate limits to keep the service stable for all users. If you exceed a limit you receive a `429` response immediately — no request is partially processed. Build your client to inspect the `Retry-After` header and pause before retrying, rather than hammering the endpoint in a tight loop.

## Limits by endpoint

Limits are counted **per API key** in fixed one-minute windows: the counter starts again at the beginning of every minute. The one exception is the keyless price feed, which is limited per IP address.

| Limit | Endpoint(s) |
|---|---|
| **100 / min** | Every request made with a key — listings, prices, games, currency, balance, order status, webhook management, P2P. This is the default; it can be raised per key. |
| **250 / min** | `POST /v1/orders` and `POST /v1/market/buy` (place buy orders and spend real money). These requests also count toward the per-key limit above. |
| **30 / min** | P2P writes — `POST /v1/p2p/listings`, `PATCH` and `DELETE /v1/p2p/listings/{id}` share one budget. A batch of up to 50 items counts as one request. These calls also count toward the per-key limit above. |
| **1 / min** | `GET /v1/prices/snapshot.ndjson.gz` (bulk compressed snapshot) |
| **3 at once** | Concurrent `GET /v1/listings/stream` connections per key |
| **1 / min per IP** | `GET /v1/public/prices` — no key, so the limit follows your IP address. The feed is rebuilt once a minute, so faster polling gains nothing. |

<Note>
  Sending 30 requests with **invalid or missing API keys** from the same IP address within one minute triggers an automatic 5-minute IP-level ban. During the ban every request from that IP returns `429 too_many_failed_auth`, whichever key it carries. Fix the key and wait out the ban before retrying.
</Note>

<Tip>
  The cheapest way to stay under these limits is to stop polling for things we can push. [Webhooks](/guides/webhooks) deliver order state as it changes, and the [SSE listing stream](/api-reference/get-listings-stream) delivers `new` and `gone` events on one connection — neither counts against your request budget per event.
</Tip>

## 429 response format

When you exceed a per-key limit the API returns:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{ "code": "rate_limit_exceeded", "detail": "Rate limit of 100 requests/min exceeded." }
```

The `Retry-After` header value is an integer number of **seconds**. On the per-key limits it is `60`: waiting that long is always enough, because the counter resets at the start of the next minute.

The bulk snapshot endpoint uses a distinct error code when rate-limited:

```json
{ "code": "snapshot_rate_limited", "detail": "Snapshot is limited to 1/min. Poll less or cache it." }
```

The keyless `GET /v1/public/prices` is limited by IP address rather than by key, and its `429` body has no `code` field — branch on the status and `Retry-After`:

```json
{ "error": "Rate limit exceeded, retry in 37 seconds", "statusCode": 429 }
```

## Handling 429s in your client

Read `Retry-After` and sleep for at least that many seconds before retrying. The example below shows a simple retry loop in bash:

```bash
while true; do
  RESPONSE=$(curl -si https://csboard.com/v1/listings \
    -H "Authorization: Bearer csb_pub_...")

  STATUS=$(echo "$RESPONSE" | head -1 | awk '{print $2}')

  if [ "$STATUS" = "429" ]; then
    RETRY_AFTER=$(echo "$RESPONSE" | grep -i "retry-after" | awk '{print $2}' | tr -d '\r')
    echo "Rate limited. Waiting ${RETRY_AFTER}s..."
    sleep "$RETRY_AFTER"
  else
    echo "$RESPONSE" | tail -1  # print body
    break
  fi
done
```

<Tip>
  Add a small jitter (e.g. `sleep $((RETRY_AFTER + RANDOM % 5))`) when running multiple workers in parallel so they don't all resume at the same instant and immediately re-trigger the limit.
</Tip>

## Raising your limits

The default limits suit most integrations. If you have a high-throughput use case — such as a data pipeline or a high-frequency trading bot — [contact us](https://csboard.com) to discuss a higher per-key limit for your account.
