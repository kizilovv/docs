API CSBoard применяет лимиты запросов на каждый ключ, чтобы сохранять стабильность сервиса для всех пользователей. Если вы превышаете лимит, то сразу получаете ответ `429` — ни один запрос не обрабатывается частично. Каждый ответ сообщает, сколько бюджета осталось в текущей минуте, так что клиент может сбавить темп ещё до лимита. Если `429` всё же пришёл, считайте заголовок `Retry-After` и сделайте паузу перед повтором, а не долбите эндпоинт в плотном цикле.

## Лимиты по эндпоинтам

Запросы с API-ключом считаются **на ключ** в фиксированных минутных окнах: счётчик обнуляется в начале каждой минуты. Лимиты ключа ниже — единственные, которые действуют на такой запрос: лимита по IP поверх них нет. У эндпоинтов без ключа, `GET /v1/health` и `GET /v1/public/prices`, считать по ключу нечего, поэтому их лимит считается по IP-адресу.

| Лимит | Бюджет | Эндпоинт(ы) |
|---|---|---|
| **100 / мин** | `read` | Чтение и любые другие запросы с ключом, кроме торговых, — листинги, стакан предмета, доступность, цены, игры, курсы валют, управление вебхуками, P2P. Это значение по умолчанию; для отдельного ключа его можно повысить по запросу. |
| **3 000 / мин** | `trading` | Торговля — `POST /v1/orders`, `POST /v1/market/buy`, `GET /v1/orders`, `GET /v1/orders/{id}`, `GET /v1/orders/info`, `POST /v1/orders/{id}/claim`, `POST /v1/orders/{id}/cancel`, `GET /v1/balance`. Если лимит чтения ключа повышен сверх 3 000, торговый лимит равен ему. Это отдельный бюджет, поэтому чтение каталога на пределе никогда не блокирует покупку или опрос статуса ордера. |
| **250 / мин** | `buy_orders` | `POST /v1/orders` и `POST /v1/market/buy` (размещают ордера на покупку и расходуют реальные деньги). Действует поверх торгового бюджета выше. |
| **30 / мин** | — | P2P-записи — `POST /v1/p2p/listings`, `PATCH` и `DELETE /v1/p2p/listings/{id}` делят один бюджет. Пакет до 50 предметов считается одним запросом. Эти вызовы учитываются и в лимите чтения выше. |
| **1 / мин** | — | `GET /v1/prices/snapshot.ndjson.gz` (массовый сжатый прайс-лист) |
| **6 / час** | — | Полные загрузки `GET /v1/listings/snapshot.ndjson.gz` (все листинги одним файлом). Ответ `304` на `If-None-Match` бесплатен. |
| **3 одновременно** | — | Параллельные подключения к `GET /v1/listings/stream` на один ключ |
| **1 / мин на IP** | — | `GET /v1/public/prices` — без ключа, поэтому лимит привязан к вашему IP-адресу. Фид пересобирается раз в минуту, так что более частый опрос ничего не даёт. |

[`GET /v1/key`](/api-reference/get-key) возвращает все лимиты ключа одним вызовом — в объекте `rate_limits`.

<Note>
  30 запросов с **неверными или отсутствующими API-ключами** с одного IP-адреса в течение минуты автоматически включают 5-минутный бан на уровне IP. Во время бана каждый запрос с этого IP получает `429 too_many_failed_auth`, какой бы ключ он ни содержал. Исправьте ключ и дождитесь окончания бана, прежде чем повторять запросы.
</Note>

<Tip>
  Самый дешёвый способ укладываться в лимиты — перестать опрашивать то, что мы можем присылать сами. [Вебхуки](/guides/webhooks) доставляют состояние ордера по мере изменений, а [SSE-стрим листингов](/ru/api-reference/get-listings-stream) присылает события `new` и `gone` по одному соединению — ни то ни другое не расходует бюджет запросов на каждое событие.
</Tip>

## Заголовки лимитов

Если ключ принят, каждый ответ несёт четыре заголовка о бюджете, который потратил запрос:

| Заголовок | Значение |
|---|---|
| `X-RateLimit-Limit` | Потолок бюджета в минуту. |
| `X-RateLimit-Remaining` | Сколько запросов осталось в текущей минуте. |
| `X-RateLimit-Reset` | Через сколько секунд окно начнётся заново, от `1` до `60`. |
| `X-RateLimit-Bucket` | `read` или `trading`. В ответе `429` от лимита на покупки — `buy_orders`. |

```http
HTTP/1.1 200 OK
X-RateLimit-Limit: 3000
X-RateLimit-Remaining: 2987
X-RateLimit-Reset: 41
X-RateLimit-Bucket: trading
```

Сбавляйте темп по этим заголовкам, а не нащупывайте потолок, упираясь в него. Когда `X-RateLimit-Remaining` дошёл до `0`, придержите запросы этого бюджета на `X-RateLimit-Reset` секунд.

## Формат ответа 429

При превышении лимита на ключ API возвращает:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 23
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 23
X-RateLimit-Bucket: read
Content-Type: application/json

{
  "code": "rate_limit_exceeded",
  "detail": "Read rate limit of 100 requests/min exceeded. The counter restarts in 23 s. For new listings use GET /v1/listings/stream instead of polling.",
  "bucket": "read",
  "limit_per_min": 100,
  "retry_after_sec": 23
}
```

`bucket` называет исчерпанный бюджет (`read`, `trading` или `buy_orders`), `limit_per_min` — его потолок. Значение заголовка `Retry-After` — целое число **секунд**: сколько осталось до начала нового минутного окна, от `1` до `60`. В `retry_after_sec` то же число. Такой паузы всегда достаточно, потому что счётчик обнуляется вместе с окном.

Эндпоинт массового снапшота цен использует отдельный код ошибки при превышении лимита:

```json
{ "code": "snapshot_rate_limited", "detail": "Snapshot is limited to 1/min. Poll less or cache it." }
```

Его `Retry-After` — тоже точный остаток минуты, как и у лимита P2P-записей (`rate_limit_exceeded`) и лимита котировок Instant Sell (`rate_limited`). В телах этих ответов только `code` и `detail`.

Четвёртый одновременный стрим листингов на одном ключе получает `429 too_many_streams` с `Retry-After: 90`. Соединение, оборванное без закрытия, держит свой слот до 90 секунд, поэтому переподключению сразу после сбоя сети, возможно, придётся подождать столько же:

```json
{
  "code": "too_many_streams",
  "detail": "At most 3 concurrent streams per key. Close an existing connection first — one stream carries the whole catalogue, so you do not need several. A connection that dropped without closing frees its slot within 90 s.",
  "max_connections": 3,
  "retry_after_sec": 90
}
```

`GET /v1/public/prices` без ключа ограничивается по IP-адресу, а не по ключу, и в теле его ответа `429` нет поля `code` — ориентируйтесь на статус и `Retry-After`:

```json
{ "error": "Rate limit exceeded, retry in 37 seconds", "statusCode": 429 }
```

## Обработка 429 в клиенте

Считывайте `Retry-After` и спите как минимум столько секунд, прежде чем повторять запрос. А лучше читайте `X-RateLimit-Remaining` в каждом ответе и сбавляйте темп, пока бюджет не кончился. Ниже показан простой цикл на bash, который делает и то и другое:

```bash
header() {
  echo "$RESPONSE" | grep -i "^$1:" | awk '{print $2}' | tr -d '\r'
}

while true; do
  RESPONSE=$(curl -si https://csboard.com/v1/listings \
    -H "Authorization: Bearer csb_pub_...")

  STATUS=$(echo "$RESPONSE" | head -1 | awk '{print $2}')

  if [ "$STATUS" = "429" ]; then
    RETRY_AFTER=$(header retry-after)
    echo "Rate limited. Waiting ${RETRY_AFTER}s..."
    sleep "$RETRY_AFTER"
  else
    echo "$RESPONSE" | tail -1  # print body

    # Последний запрос этой минуты: дождитесь нового окна перед следующим.
    if [ "$(header x-ratelimit-remaining)" = "0" ]; then
      sleep "$(header x-ratelimit-reset)"
    fi
    break
  fi
done
```

<Tip>
  Добавьте небольшое случайное смещение (например, `sleep $((RETRY_AFTER + RANDOM % 5))`) при запуске нескольких воркеров параллельно, чтобы они не возобновляли работу одновременно и не срабатывали по лимиту снова.
</Tip>

## Опрос или стрим

[Стрим листингов](/ru/api-reference/get-listings-stream) публикует событие `new` примерно через 0,3 секунды после того, как листинг появился в каталоге. Замер 26 октября 2026 года: медиана 0,34 с, максимум меньше 0,5 с. Как бы часто вы ни опрашивали `GET /v1/listings`, листинг не появится у вас раньше, чем его доставит стрим. Все ключи получают один и тот же стрим в один и тот же момент — приоритетного уровня нет.

- Для новых листингов и событий `gone` держите открытым один стрим. Переподключайтесь с `Last-Event-ID` или начинайте с `X-Stream-Position` [снапшота листингов](/api-reference/get-listings-snapshot) — так вы ничего не пропустите.
- Для выборок с фильтрами — один предмет, диапазон float, ценовой коридор — используйте `GET /v1/listings`.

## Повышение лимитов

Стандартные лимиты подходят для большинства интеграций, но если у вас сценарий с высокой нагрузкой — например, конвейер данных или высокочастотный торговый бот — [свяжитесь с нами](https://csboard.com), чтобы обсудить более высокий лимит на ключ для вашей учётной записи.
